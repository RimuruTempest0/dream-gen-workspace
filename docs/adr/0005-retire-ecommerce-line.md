# 停掉电商版，只保留大众版

2026-11-20，已采纳。修订 ADR 0001、0002、0003 里“两条产品线”的前提，各条修订见下文“对旧决定的影响”。

## 背景

仓库里原有两条产品线：电商版在 `main` 分支（停在 0.7.18），大众版在 `creative-concepts` 分支（0.8.0），共用一个管理工具。提供方决定只做大众版。

决定时核对过的事实：

- 管理工具台账里的 8 个人全是大众版托管版顾客，没有电商版客户；`release/customers/` 里的交付包也都是大众版。
- `main` 上唯一没进大众版的提交（0.7.18，样板核对改用 Messages API 的图片格式）在大众版里已有同样的修复。
- GitHub 上没有电商版的 Latest Release，已交付的电商版程序本来就读不到在线更新。

## 决定

1. **电商版整条产品线停掉**：不再出包、续费、修 bug。
2. **删除 `main` 分支，不打标签。** 电商版的代码不再保留在任何分支或标签上；已合并 PR 留下的引用不主动清理。
3. **`creative-concepts` 改名为 `main`**，并设为 GitHub 默认分支。管理工具从 `main` 构建大众版。
4. **管理工具只管大众版**（1.12.0）：删掉电商版的交付包构建、更新清单地址设置、“发布程序更新”（格式 1 清单）和新建时选产品线；名单里只有托管版顾客，界面统一叫“顾客”。台账里没有产品线标记的旧记录视为电商版，不能再出包或生成授权文件。
5. **产品继续叫“大众版”。** 已经写进发出去的程序、改不了的标识照旧：更新清单格式 2、清单里的产品线 `creative`、发布位标签 `creative`。

## 为什么

- 没有在用的电商版客户，维护第二条线只剩成本：每次改共用代码要考虑两边，管理工具要多一套构建目录和出包流程。
- 不打标签是提供方的选择：电商版不打算再拿回来，干净比可追溯更重要。代价见“后果”。
- 分支改名为 `main`，是为了不让人以为还有另一条线；GitHub 会把旧名字转到新名字，未合并的 PR 自动改到新分支。
- 产品名和 `creative` 标识不改：发布位地址和产品线名已经写进发出去的程序（ADR 0001 的教训），改名只会让已交付的大众版收不到更新。

## 对旧决定的影响

- **ADR 0001**：清单格式 1/2 的隔离、固定的 `creative` 发布位、共用签名密钥都保留。“不能干扰已交付的电商版客户”这一理由只剩一点：`creative` Release 仍须是 Pre-release、不是 Latest，因为已交付的电商版旧程序每天读 Latest；它们只认格式 1，即使读到也不会装上大众版。
- **ADR 0002**：每条产品线一个构建目录，变成只有大众版一个（`<源码目录>-build\creative`），从 `main` 构建。源码目录只读、构建结果严格对应提交、构建目录里的改动下次被丢弃等理由仍然成立。`-build\ecommerce` 已删除。
- **ADR 0003**：开源版和托管版是同一个程序这一点不变。第 9 条“电商版客户和托管版顾客在同一个名单、新建时选产品线”作废：名单里只有托管版顾客。

## 后果

- 电商版的源码只能从已合并 PR 的引用里零星找回，找不回完整的 `main`。需要时只能从大众版重新做。
- 外面若还有电商版程序在用，它们收不到更新、续不了费；授权文件到期后停止出图。提供方确认没有需要继续服务的人。
- 删掉了只在真实环境里构建电商版客户包的手动集成测试（`real_build_test.go`）。大众版托管包的组装由 Go 测试和管理工具桌面测试覆盖。
