# 两条产品线各在自己的构建目录里构建，管理工具不切换源码目录的分支

2026-11-17，已采纳。2026-11-20 由 ADR 0005 修订：电商版已停掉，只剩大众版的构建目录（`-build\creative`），从改名后的 `main` 分支构建；本文关于电商版和 `creative-concepts` 分支的内容只作历史。

## 背景

电商版在 `main` 分支，大众版在 `creative-concepts` 分支，都由同一个管理工具构建。管理工具 1.6 只认一个源码目录：生成客户交付包要求它在 `main`，发布大众版要求它在 `creative-concepts`，并且都要求没有未提交的改动。提供方平时在 `creative-concepts` 上开发，每次给电商版客户出包都要先提交或搁置手头的改动、手动切分支、出完包再切回来。提出的需求是“在管理工具里加切换分支的功能”。

## 决定

1. **不做切换分支的功能。** “生成交付包”永远构建电商版，“发布大众版”永远构建大众版，按钮旁显示将要构建的版本号和提交。
2. **每条产品线一个构建目录。** 管理工具在源码目录旁维护 `<源码目录>-build\ecommerce` 和 `<源码目录>-build\creative`（Git worktree），每次构建前把它对准该产品线本机分支的最新提交，在里面运行那个提交自己的 `scripts/build.ps1`。
3. **管理工具对源码目录只读。** 它不在源码目录里切分支、提交、拉取或推送。源码目录里未提交的改动不拦构建，只提示它们不会进包。
4. **构建目录归管理工具所有。** 里面的任何改动在下次构建前被丢弃。
5. **工具链、依赖和产出不复制。** 构建目录里的 `.tools`、`frontend\node_modules`、`release` 是指向源码目录的目录链接，所以产出仍然落在源码目录的 `release\` 下。
6. **版本号取自被构建的提交。** 客户交付包和大众版一样，按该产品线源码里 `wails.json` 的版本号构建，不能另填。
7. **构建目录建不起来就报错。** 不退回到在源码目录里原地构建。一次只进行一个构建。
8. **管理工具自己的源码以 `creative-concepts` 为准。** `main` 上那一份不维护，也不为管理工具的改动去动 `main`。

## 为什么

- 在界面里手动切分支，只是把命令行里的一步搬了个地方，仍然会忘、会切错。
- 构建时自动原地切换、构建完再切回来，实现最简单，但构建的几分钟里源码目录是另一条产品线的代码：这个仓库里经常有 AI 代理在改文件，会改到错的分支上；构建中途失败或管理工具被关掉，目录会停在另一个分支；有未提交改动时仍然出不了包。
- 构建目录让“发出去的包严格等于某个提交”这件事不再依赖源码目录当时的状态，所以第 4 条必须成立，第 3 条里的拦截也就没有必要了。
- 链接而不是复制：`.tools` 有 4G 多，`release\` 有 20G 多，而且台账里的路径、从客户包数据排查问题的做法都指向源码目录的 `release\`。两个分支的前端锁文件和 `go.mod` 相同，共用依赖是安全的。
- 版本号手填时，可以把 `main` 上 0.7.17 的代码标成 0.7.33 发出去（这正是提出这个需求时差点发生的事）。
- 留着原地构建作为退路，等于保留两套行为，退回去时又会遇到分支不对的问题。
- 管理工具管两条产品线，但源码只能跟着某个分支走。每次同步到 `main` 多一步且容易漏；拆成单独的分支或仓库现在不值得。

## 后果

- 电商版要出新版本，必须先在 `main` 上提交（至少改 `wails.json` 的版本号）。管理工具不替你做这一步。
- 管理工具必须能调用 `main` 上那份较旧的 `scripts/build.ps1`。给构建脚本加参数时要考虑两个分支上的版本。
- 两个分支的前端依赖或 Go 依赖一旦不同，共用的 `node_modules` 和模块缓存就不再可靠，需要改成每个构建目录各装一份。
- `git worktree list` 会多出两个条目；源码目录旁多一个 `-build` 文件夹。删除构建目录前要先删掉里面的三个链接，否则在资源管理器里删除会连同源码目录的 `.tools` 和 `release` 一起删掉。文件夹里的 `说明.txt` 写了这一点。
- 在管理工具之外直接运行 `scripts/build.ps1`（本机开发版）不受影响，仍然构建源码目录里当前检出的代码。
