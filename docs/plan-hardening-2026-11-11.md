# 改进与安全加固执行计划（2026-11-11）

来源：2026-11-11 对 0.7.9 的代码审阅。覆盖“可加强/优化”8 项（I1–I8）和“安全”7 项（S1–S7）的全部内容。
按阶段执行，每个阶段独立可交付；前一阶段验证通过后再进入下一阶段。

## 通用约束（每个阶段都适用）

- 先读 `AGENTS.md`、`README.md`、`docs/local-development-profile.md`，严格遵守。
- 构建只用 `scripts/build.ps1 -Version '版本号'`（管理工具用 `scripts/build-admin.ps1`）；不绕过、不删除 `scripts/packcheck`；改动打包内容时同步更新它的允许清单。
- 每个交付阶段升一次版本：应用版本跟随 `wails.json`（当前 0.7.9），管理工具单独计版本；分别写入 `docs/CHANGELOG.md` 和 `docs/CHANGELOG-admin.md`，同步 `README.md` 和 `docs/使用说明.txt`。
- 测试和桌面 QA 只用隔离数据目录与本机模拟服务。**不调用真实付费接口**，不读写用户实际数据目录，不删除 `release/` 下任何数据目录或 `data-location.txt`。
- Key、激活码、签名私钥不写入源码、文档、日志、对话或发布包。
- `internal/core/builtin_skills/` 和 Agent 提示词里看不懂的改动可能是 ChatGPT 正在进行的工作：不要回退；要改技能正文前先停下来问用户。
- 不提交、不推送 git，除非用户在该会话里明确要求。
- 每阶段完成的标准：`go test ./...`、`go vet ./...`、`pnpm --dir frontend run typecheck`、`pnpm --dir frontend exec prettier --check src` 全部通过；涉及界面的改动跑 `scripts/desktop-qa.ps1` + `pnpm --dir frontend run test:e2e`；改了本机配置保留流程则跑 `scripts/test-local-profile.ps1`。
- 旧的客户包（`customer.dat` format 2）和旧数据目录必须继续可用；数据库结构变化要提升 `PRAGMA user_version` 并写迁移和测试。

## 阶段 1 · 客户版保护与小改进（S3、S4 后半、I5、I6）

**S3 隐藏客户版技能内容**（0.7.10 实现；2026-11-11 用户决定不隐藏：技能本身是开源的，客户可以查看、编辑、停用。0.7.17 已撤回，已封存的数据自动还原）
- 现状：`ListSkills`（`internal/core/skills.go:298`）不区分授权模式，客户可在设置里查看、编辑、导出内置技能；备份（`internal/core/backup.go`）里也有明文。
- 做法：授权模式不是 developer 时，
  - `ListSkills` 对内置技能只返回名称、说明、启用状态，不返回正文和附件内容；`SaveSkill`/`DeleteSkill`/导出对内置技能拒绝；
  - 前端 `AgentSettings.tsx` 对应隐藏“查看/编辑”，只留启停；
  - 内置技能不再以明文写入数据目录 `skills/` 和备份（运行时从内嵌内容读取；客户自己导入的技能照旧）；
  - 运行活动、日志、LLM 监控导出中不出现技能正文（检查 `run_activity.go`、`llm_monitor.go`、`logs.go`）。
- 开发者模式行为不变。说明：EXE 内嵌的明文仍能被逆向取出，彻底解决要靠阶段 7 的服务器端下发，这里先挡住“打开设置就能复制”。
- 测试：客户模式下各接口不泄露正文；开发者模式不变；备份 ZIP 不含内置技能正文；`customer.spec.ts` 增加界面检查。

**S4（后半）运行时校验随包组件**
- 现状：`claude.exe` 和 `product-browser.exe` 的哈希只在构建时写进 `version.json`，运行时不校验。
- 做法：构建时把两个文件的 SHA256 通过 `-ldflags -X` 写入主程序（`scripts/build.ps1` 需先构建 `product-browser.exe` 再构建主程序）；启动 Agent 或浏览器辅助程序前校验，不一致则拒绝运行并提示重新解压完整包。未注入哈希的开发构建跳过校验。
- 测试：哈希不符时拒绝启动的单元测试；QA 构建不受影响。

**I5 一键导出诊断包**
- 在“日志”页加“导出诊断包”：ZIP 内含最近日志（已脱敏）、版本信息（`version.json`）、授权模式和软件标识、线路名称与健康状态、系统版本、最近失败任务的错误信息。
- 不含 Key、激活码、提示词、图片、技能正文、`customer.dat`。用 `internal/packcheck` 同类检查写测试确认。

**I6 用量与成本可见**
- 激活后也显示主图片线路的上游剩余额度（现在 `licenseStatusLocked` 只在 trial 时刷新，`internal/core/license.go:335`）。
- 智能生图“开始生成套图”前显示预估：张数 × 最近同模型同尺寸的平均值（来自已有的中转站监控/LLM 监控记录）；没有历史数据时不显示数字，不编造价格。

## 阶段 2 · 性能与工程维护（I4、I8）

**I4 数据量增大后的性能**
- 现状：`objects` 表只有 `(kind,id)`，`List[Task]` 每次读出并反序列化全部任务（`internal/core/store.go:88`），`licenseStatusLocked`、`trialStopLocked`、队列调度等在全局锁 `s.mu` 内反复调用。
- 做法：
  - 先写基准测试（5,000 和 50,000 条任务）定位热点，再改；
  - 给任务加可索引的状态/批次/试用标记列（或独立计数表），由 `Put`/`Submit` 维护；试用计数、队列取下一条、最近批次列表改为按索引查询，不再全表反序列化；
  - 提升 `user_version` 到 2，启动时一次性迁移旧数据，迁移可重入；旧版本打开新库的提示保持现有逻辑。
- 完成标准：基准测试在 50,000 条任务下，状态查询和调度单次耗时不随任务数线性增长；原有测试全部通过。

**I8 工程维护**
- CI：新增 `.github/workflows/ci.yml`（Windows runner）跑 Go 测试、vet、前端 typecheck、prettier。不在 CI 里构建发布包，不放任何密钥。
- 拆分大文件，不改行为：`frontend/src/App.tsx`（按页面拆：工作台、素材库、任务、设置）、`SmartImages.tsx`、`styles.css`（按页面/组件拆）；`internal/core/service.go` 按职责拆文件。拆分后 e2e 全过，界面截图无差异。
- 整理 `docs/`：历史截图和 `validation-*.json` 移入 `docs/archive/`，更新引用。

## 阶段 3 · 授权格式升级：到期（S2 的离线部分）

- `internal/license` 新增 format 3：`Profile` 增加 `ExpiresAt`（可空 = 不过期）。应用同时接受 format 2 和 3。
- 应用：过期后进入新的 `expired` 模式，停止新的生成，已有图片和导出照常；到期前 7 天提示。记录“见过的最晚时间”（和试用计数同样存放在 DPAPI 文件 + 注册表），系统时间回拨到它之前时按已过期处理。
- 管理工具：客户增加有效期字段（把现在的备注 `PlanNote` 里的有效期变成真实字段），续费 = 生成新的 `customer.dat`（只发这个小文件即可，不必重发整包）；应用支持在“连接与设置”里导入新的 `customer.dat`（验签通过且软件标识一致才替换）。
- 设备绑定、吊销、试用防重置离线做不到，放到阶段 7。
- 测试：format 2 旧包照常；到期、临期提示、时间回拨、续费导入、软件标识不一致被拒。

## 阶段 4 · 更新机制与运行时（I1、S5）

**I1 小体积更新与新版本提示**
- 构建额外产出“程序更新包”：只含 `ImageWorkbench.exe`、`product-browser.exe`、`使用说明.txt`、`version.json`（运行时和 `agent` 变了才带）；完整包照旧。`scripts/packcheck` 允许清单同步。
- 更新清单：管理工具生成用现有 Ed25519 签名密钥签名的 `update.json`（版本、更新包 SHA256、最低可升级版本、说明、下载地址）。清单地址在构建时注入；未注入则不检查更新。
- 应用：启动后和每 24 小时检查一次清单（只读、可在设置里关闭），验签通过才提示“有新版本”；用户确认后下载、校验 SHA256、退出并由一个小的替换步骤覆盖程序文件再重启，保留 `data`、`data-location.txt`、`customer.dat`。有活动任务时不更新。失败可回滚到旧文件。
- 清单和更新包放在哪里由用户决定（见“需要用户处理的事项”）；本阶段用本机模拟服务测试完整流程。

**S5 固定版 WebView2 的更新**
- `build.ps1`：读取运行时版本，超过 90 天未更新时构建给出明显警告（不阻断）；文档写明获取新版 Fixed Version 运行时的步骤。
- `cmd/product-browser`：确认并收紧——独立用户数据目录（已有）、禁用下载、禁用弹窗新窗口、禁用密码保存与自动填充、只允许 http/https 导航、页面读取完成即关闭。逐项写入 `scripts/test-product-browser.ps1`。
- 运行时过旧也纳入阶段 4 的更新包判断（运行时版本变化时更新包带上 `runtime`）。

## 阶段 7 · 自有网关（S1、S2 在线部分、S6）

目标：真实上游 Key 不再进入客户包；可吊销、可到期、可绑定设备、按客户计量；试用计数放在服务器。

1. **先写设计文档** `docs/gateway-design.md` 并停下来给用户确认（部署环境、域名、是否接受客户端必须联网、计费口径），确认后再实现。
2. 服务端 `cmd/gateway`（Go，单二进制 + SQLite）：
   - 客户令牌（每客户一个，可轮换）、设备登记（每客户设备数上限）、到期时间、停用开关；
   - 代理图片和 LLM 请求到上游（流式透传），按主备顺序切换，服务器端保存上游 Key；
   - 按客户记录用量（张数、tokens），试用额度在服务器端扣减；
   - 管理接口只供管理工具使用，单独的管理员令牌；全程 HTTPS；限速；日志脱敏。
3. 客户端：`customer.dat` format 3 新增“网关线路”——只含网关地址和客户令牌（令牌首次激活时与设备标识绑定，之后由 DPAPI 保存）。应用对网关线路沿用现有健康检查、切换、监控逻辑。旧的直连线路（format 2）继续支持。
4. 管理工具：客户、Key 池、有效期、设备、用量与网关同步；可一键停用客户；交付包检查确认不含任何上游 Key。
5. （已取消：用户决定内置技能对客户可见，不再由网关下发。）
6. 测试：本机起网关 + 模拟上游，覆盖吊销、到期、超设备数、试用扣减、主备切换、流式中断；不调用真实上游。
7. 部署由用户完成；提供部署说明和备份方法。

## 阶段 8 · 代码签名（S4 前半）

- `scripts/build.ps1` 和 `scripts/build-admin.ps1` 增加可选签名步骤：传入证书指纹（或环境变量）时用 `signtool` 给 `ImageWorkbench.exe`、`product-browser.exe`、`ImageWorkbenchAdmin.exe` 签名并加时间戳，签名后才计算 `version.json` 里的哈希和阶段 1 的内嵌哈希；未提供证书时给出警告继续构建。
- 构建结束用 `Get-AuthenticodeSignature` 验证。证书由用户购买（见下）。
- 验签公钥被二进制修改替换的问题：签名后修改会使签名失效；应用启动时校验自身签名状态（有签名的构建才启用），失效则拒绝加载 `customer.dat`。
