# 管理工具更新记录

管理工具（`ImageWorkbenchAdmin.exe`）从 1.0.0 起有自己的版本号，写在 `internal/admin/version.go`，显示在工具左下角。软件的版本号写在 `wails.json`，说明见 `docs/CHANGELOG.md`；交付包按软件版本命名。只改管理工具时升管理工具的版本，软件版本不变。

## 1.12.0 · 停掉电商版，只管大众版

软件版本不变。电商版整条产品线停掉（`docs/adr/0005-retire-ecommerce-line.md`），管理工具只管大众版。

- **分支**：大众版的分支 `creative-concepts` 改名为 `main`，管理工具从 `main` 构建大众版。1.11.0 及更早的管理工具还在找 `creative-concepts`，请换成 1.12.0。
- **顾客页**：原来的“客户与顾客”改成“托管版顾客”，新建时不再选产品线，新建的都是托管版顾客。名单里没有“产品线”一列。
- **交付包**：“生成交付包”只组装托管版的包（最新构建的大众版程序加这位顾客的授权文件），不再为某个人单独构建程序。“只生成授权文件”在分配好 Key 后随时可用，不用先出包。
- **去掉的功能**：电商版的交付包构建、`<源码目录>-build\ecommerce` 构建目录、“设置与签名密钥”里的“程序更新”（更新清单地址和“发布程序更新”）。大众版的发布照旧在“发布大众版”页。
- **旧记录**：台账里没有产品线标记的记录属于电商版，不能再生成交付包或授权文件，页面上会说明。现有台账里没有这种记录。
- **叫法**：管理工具里“客户”一律改称“顾客”。
- 上传大众版时仍然要求 `creative` Release 是 Pre-release、不是 Latest：已交付的电商版旧程序每天读 Latest。

### 验证范围
Go 测试全部通过（`internal/admin`）：构建目录用真实 Git 仓库，只从 `main` 构建大众版，源码目录在其他分支、有未提交改动时都不受影响；`ecommerce` 不再是可构建的产品线；新建的人都是托管版顾客；没有产品线标记的旧记录出不了包、也生成不了授权文件；原来走电商版出包的测试（Key 检查、换 Key、删除顾客、批量操作、有效期与续费、包内不含 Key）改为先构建大众版再组装托管版的包。管理工具桌面测试 3 项通过（隔离数据和替身源码仓库，不连 GitHub）：新建顾客没有产品线选项，构建大众版 0.7.34 后组装托管版的包、包内有授权文件且没有 Key 和激活码明文、没有 `-build\ecommerce`；发布大众版页显示 `main` 分支；含无障碍检查。删掉了只构建电商版客户包的手动集成测试 `real_build_test.go`。没有做的：没有用真实构建脚本跑一次大众版构建。

## 1.11.0 · 发布大众版：在管理工具里上传到 GitHub

软件版本不变。以前构建完要自己到 GitHub 网页上传两个文件，现在管理工具可以替你传。

- **“上传到 GitHub”**：“发布大众版”页的表格里每个构建过的版本都有这个按钮；刚构建完时，提示条上也有“上传”。点了先弹确认框，写明要传的两个文件（按顺序、带大小）、传到标签为 `creative` 的 Release，以及 Release 上现在是哪个版本。
- **上传做什么**：先确认 `creative` Release 仍是 Pre-release、不是 Latest；确认两个文件和构建时签名的一致；先传更新包，再替换 `update.json`；最后从公开地址把两个文件读回来逐字节核对。全部通过后表格里显示“已上传”和时间。进度显示在页面上的上传记录里。
- **会拒绝的情况**：Release 不是 Pre-release 或成了 Latest（电商版客户的软件每天读 Latest）；Release 上已经是更新的版本（不能往回退）；更新包或 `update.json` 在构建之后被改动过；Release 上现有的 `update.json` 不是这把签名密钥签的大众版清单。更新包传失败时不会替换 `update.json`，顾客仍然看到原来的版本。
- **用什么上传**：本机已登录的 GitHub CLI（`gh`），管理工具自己不保存 GitHub 的登录信息。没有安装或没有登录时会说明怎么做。
- 同一版本可以重新上传（例如上次读回核对没通过时）。完整包从不上传。手工在网页上传仍然可以，步骤见 `docs/release-github.md`。

### 验证范围
Go 测试（替身发布位）：按“更新包、`update.json`”的顺序上传，读回一致后记为已上传；同一版本可重传，确认信息里能读出 Release 上现在的版本；Release 不是 Pre-release、是 Latest、上面是更新的版本、要传的版本没构建过时都拒绝且什么都不传；更新包构建后被改动时拒绝；更新包上传失败时不替换 `update.json`；读回内容不一致时报错且不记为已上传。另对真实的 `creative` Release 做了只读检查：能读出它是 Pre-release、不是 Latest、上面的 `update.json` 是 0.7.38，读不存在的文件得到“未发布”。管理工具桌面测试 3 项通过（隔离数据，替身发布位，不连 GitHub）：构建后点“上传到 GitHub”，确认框列出两个文件和“还没有 update.json”，上传后显示已核对、表格显示已上传、“还没有上传”的提示消失；再点一次时确认框说明 Release 上已经是这个版本；含无障碍检查。没有做的：没有用管理工具对真实的 GitHub 实际上传过一次。

## 1.9.0 · Key 池：已在上游注销的 Key 单独一类

软件版本不变。交付过的 Key 在上游后台注销后已经没用，但以前只能停用、不能删除，一直混在列表里。

- **新的状态“已注销”**：在 Key 池勾选 Key，点“标记为已在上游注销”。这些 Key 移到单独的“已注销”分类，不再出现在“全部状态”“可用”“已停用”等列表里；“全部状态”下方提示还有几个已注销的 Key。
- **只留记录**：已注销的 Key 不能分配、不能重新启用，“停用所选”也不会改动它们。记录和本机加密保存的 Key 都保留，所以同一个 Key 仍然不能再次导入、分给另一位客户，发布大众版时的检查也照样包括它们。交付过的仍然不能删除；从没交付过的可以删除。
- **标记错了**：在“已注销”分类里勾选，点“撤销注销标记”，Key 回到“已停用”；要再分配，先到上游后台确认，再逐个重新启用。
- 正分配给客户的 Key 不能标记为已注销，要先在客户页撤下。所选里有这种 Key 时，整批都不会改动。

### 验证范围
Go 测试：正分配的 Key 不能注销，整批不改动；交付过并已停用的 Key 和从没用过的 Key 一起注销后都有注销时间；已注销的 Key 不能重新启用、不能分配，停用不会改掉注销状态；同一个 Key 不能再次导入；交付过的已注销 Key 不能删除；撤销标记只接受已注销的 Key，撤销后回到已停用。管理工具桌面测试 3 项通过（隔离数据）：在原有客户流程最后，把剩下交付过的 Key 全选标记为已注销，它们从列表里消失，“全部状态”显示另有几个已注销，“已注销”分类里只有它们，批量栏只有“撤销注销标记”，撤销一个后少一个；含无障碍检查。没有用你的真实台账试。

## 1.8.0 · 给大众版的顾客出托管版的包

- **新建时选产品线**：“客户”页改名“客户与顾客”，新建时选“电商版”或“大众版 · 托管版”，创建后不能改。列表多一列“产品线”，可以筛选。已有的人全部算电商版。Key 池共用。

- **生成托管版交付包不重新构建**：用“发布大众版”里最新构建的那一版程序，加上这位顾客的授权文件，几秒钟出包。页面上写明用的是哪一版、什么时候构建的。产出仍在 `release\customers\软件标识\ImageWorkbench-名称-版本号.zip`。

- **只生成授权文件**：顾客已经装了大众版（0.7.34 或更高）时，不用发整包，只发 `customer.dat`，对方在软件里导入并输入激活码。电商版仍然要先有交付包才能生成续费授权文件。
- 交付包照旧检查：没有明文 Key，没有本机连接。授权文件不会写进 `release\creative\build\…`（下一次构建大众版要拿它做比较）。
- 界面上几处“客户”改成了不分产品线的说法；其余文字仍然用“客户”，对托管版顾客同样适用。

## 1.7.0 · 两条产品线各在自己的构建目录里构建，不用再切分支

软件版本不变。在 `creative-concepts` 分支上给电商版客户点“生成交付包”，1.6 会提示“请先切换分支再试”。这一版起不用切：管理工具为每条产品线在源码目录旁维护一个构建目录，取舍见 `docs/adr/0002-build-folders-per-product-line.md`。

- **构建目录**：`<源码目录>-build\ecommerce`（电商版，`main` 分支）和 `<源码目录>-build\creative`（大众版，`creative-concepts` 分支）。每次构建前，对应的目录被恢复成该分支本机的最新提交，然后在里面构建。第一次构建时自动创建。
- **源码目录只读**：管理工具不再要求源码目录在某个分支，也不在里面切分支、提交、拉取或推送。源码目录里有未提交的改动时不再拒绝构建，只提示“不会进入这次构建”。
- **按钮旁显示将要构建的代码**：版本号、分支、提交的短哈希、标题和时间。“生成交付包”和“发布大众版”两处都有。构建记录的第一行也写明构建的是哪个提交、构建目录在哪。
- **客户交付包的版本号不能再手填**：取自 `main` 分支最新提交的 `wails.json`（现在是 0.7.17）。要给电商版出新版本，先在 `main` 上提交。
- **产出位置不变**：仍在源码目录的 `release\customers\…` 和 `release\creative\…`。构建目录里的 `.tools`、`frontend\node_modules`、`release` 是指向源码目录的链接，没有复制。
- **构建目录里的改动会被丢弃**：它只用来构建。`<源码目录>-build\说明.txt` 写了这一点，以及删除构建目录前要先删掉那三个链接。
- **建不起构建目录就报错**（没装 Git、磁盘满、目录被占用等），不会退回到在源码目录里构建。同一时间仍然只进行一个构建。
- “发布大众版”预填的更新说明，改为取自 `creative-concepts` 分支最新提交里的 `docs/CHANGELOG.md`，不再读源码目录里可能没提交的那份。

### 验证范围
Go 测试，用真实的 Git 仓库（两个分支、版本号不同、路径带中文和空格）：构建目录里是该产品线的提交；工具链、前端依赖和 `release` 能通过链接用到，写进构建目录 `release` 的文件出现在源码目录的 `release` 里；在构建目录里改、删、加的文件下次构建前都被恢复；构建目录损坏后会重建；整个过程中源码目录的分支、未提交的改动和 `release` 下已有的文件都没有变；构建目录里链接的位置如果是一个有内容的真实文件夹，拒绝构建且不删除它。另有测试覆盖：两条产品线各取自己分支的提交和各自的构建目录；另一条产品线的未提交改动不提示；版本号与源码不一致时拒绝；构建目录准备失败时不构建。管理工具桌面测试（隔离数据，替身源码目录停在 `creative-concepts`、`main` 是 0.6.2、`creative-concepts` 是 0.6.3）2 项通过：客户流程里交付包按 `main` 的 0.6.2 构建，源码目录仍是 0.6.3；“发布大众版”显示提交、未提交改动只提示不拦、构建后源码目录的分支和改动原样保留，含无障碍检查。真实构建一次：源码目录停在 `creative-concepts` 时，用 `main` 上的构建脚本在 `D:\image_workplace-build\ecommerce` 里构建出电商版 0.7.17 的完整客户包（264 个文件，测试用的假 Key，隔离的管理工具数据），包内程序认管理工具的公钥、授权文件能激活，构建后测试产出已删除。没有调用真实付费接口，没有上传任何文件。没有做的：没有对真实源码跑一次大众版的构建（它走同一段代码，但 `creative` 构建目录要到你第一次点“构建大众版”时才创建）；没有在已安装的管理工具界面里手点一遍。

## 1.6.1 · “构建大众版”在检查更新包时失败

1.6.0 第一次对真实源码构建大众版时，在“检查更新包”一步失败，提示无法创建 `runtime\EBWebView` 文件夹。原因：构建脚本用 PowerShell 打包，压缩包里的文件夹条目以反斜杠结尾，解包时被当成了文件，随后同名的文件夹就建不出来。只有更新包带浏览器运行组件时才会出现（第一次构建没有上一版可比，一定会带），1.6.0 的测试用的包里没有文件夹条目，所以没有发现。

- 解包和“发布程序更新”读取更新包时，都把这类条目当作文件夹跳过。
- 这段解包代码也在软件里：0.7.32 的软件安装带运行组件的更新包时会遇到同样的失败。修复已包含在 0.7.32 里（这一版还没有发出去，版本号不变）。

### 验证范围
Go 测试新增：含反斜杠文件夹条目的包能解开，文件夹下的文件在。另用本机真实构建出的完整包（含这些条目）解包一次，运行组件和 Claude Code 的文件都在。没有做的：没有重新用管理工具对真实源码跑完整的“构建大众版”，这一步需要你再点一次。

## 1.6.0 · 发布大众版，按产品线检查分支

配合软件 0.7.32。管理工具从这一版起同时管两条产品线，源码以 `creative-concepts` 分支上的为准。

- **新页面“发布大众版”**：显示源码目录的版本号、当前分支和未提交的改动；从 `docs/CHANGELOG.md` 取这一版的条目预填更新说明（可以改）；点“构建大众版”后构建程序、检查两个包、生成签名的 `update.json`。
- **产出**在 `release/creative/版本号/`：完整包 `ImageWorkbench-版本号.zip` 留在本机，由你私下发；`upload` 文件夹里正好两个文件，更新包 `ImageWorkbench-update-版本号.zip` 和 `update.json`，只有这两个要上传。程序文件夹在 `release/creative/build/版本号/`，下一次构建靠它判断更新包要带什么。
- **不上传**：管理工具不碰 GitHub。页面上写了上传步骤，并有按钮打开标签为 `creative` 的 Release。
- **更新包的检查**：只含程序文件；是大众版的构建；版本号与源码一致；不带内置 Claude Code；不含本机的连接和 Key，也不含 Key 池里的任何一个 Key。任何一项不过，`upload` 文件夹和完整包都会被删除。
- **分支检查**：构建大众版要求源码目录在 `creative-concepts` 分支；生成客户交付包（电商版）要求在 `main` 分支。两者都要求没有未提交的改动，否则拒绝并说明原因（列出文件）。`.claude/` 下的本机工具文件不算改动。需要本机装有 Git。
- **版本号**：大众版按源码里 `wails.json` 的版本号发布，不能另填。
- 大众版的更新清单是格式 2、写明产品线，和电商版共用签名密钥；“设置与签名密钥 → 发布程序更新”仍然只生成电商版的格式 1 清单。

### 验证范围

## 1.0.0 · 与软件分开版本号；Key 池批量停用和批量删除

- **分开版本号**：管理工具不再占用软件版本号，左下角显示“管理工具 1.0.0”。“生成交付包”里的“软件版本”仍读取 `wails.json`，现在是 0.6.19。
- **样式分开**：管理工具专用的样式移到 `frontend/src/admin/admin.css`，不再进入软件的样式文件。
- **勾选多个 Key**：Key 池“全部 Key”表格每行前加了复选框，表头复选框选择本页，旁边的下拉可以选择全部或清空。勾选后表格上方出现“已选 N 个 Key”和“停用所选”“删除所选”“取消选择”。切换筛选时清空勾选，批量操作只作用于当前筛选显示的 Key。
- **批量停用**：选中的 Key 一起停用（原因记为“手动停用”），已经停用的保留原来的原因。所选里有正在分配给客户的 Key 时按钮不可用，并提示先在客户页撤下。
- **批量删除**：只能删除从未交付过的 Key（可用或手动停用的），从 Key 池和本机加密存储中一起删除，无法恢复，以后可以重新导入。所选里有已分配或交付过（含“曾交付”）的 Key 时按钮不可用，并说明原因：交付过的 Key 的记录用来防止同一个 Key 被重新导入、分给第二位客户，只能停用。
- 后台也做同样检查：所选中任何一个不符合条件时整批都不改动。

这些批量功能曾以软件版本 0.6.20 发布（只改了管理工具）。软件版本已退回 0.6.19；已生成的 0.6.20 交付包仍可使用，只是版本号显示为 0.6.20，并多带一段软件用不到的管理工具样式。软件下一个版本从 0.6.21 开始，避免与这些包重名。

### 验证范围
Go 测试：批量删除选中交付过或已分配的 Key 时整批被拒绝、什么都不改；批量停用选中已分配的 Key 时被拒绝；批量停用保留已停用 Key 的原因；批量删除后 Key 记录和本机密钥文件都被删除；空选择被拒绝。管理员工具桌面测试（隔离数据）：筛选“可用”后全选，包含“曾交付”的 Key 时删除按钮不可用并显示原因，批量停用后列表清空；再筛选“已停用”，勾选从未交付的 Key 批量删除，“曾交付”的 Key 保留；勾选状态下的无障碍检查通过。没有调用真实付费接口。
